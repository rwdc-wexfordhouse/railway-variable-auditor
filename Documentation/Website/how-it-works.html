How it works

What the audit reads, the files it writes, and how to work through them.

What is built

The audit is built: the window and the command line program both sign in through the Railway CLI, find every workspace you can access, and write every variable with its value to one CSV file. It is tested against a fake Railway CLI and a fake Railway. It has not yet been run on the author’s live account. Run it yourself and check the result. Rotating variables, staging, deploying and undo were started and then set aside: the code is still in the source tree, but no program uses it and it is not documented as a feature.

Why this exists

On 21 October 2026 Railway disclosed that an unauthorised third party “may have accessed encrypted environment variables and, for some of them, obtained the decrypted contents”. Railway says the impact may be limited to a subset of users, and recommends that everyone acts. Read Railway’s disclosure. Treat every variable value as possibly exposed.

Railway advises rolling every environment variable. To do that you first need to know what you have. This tool gives you the whole list, in one file, so you can work through it.

Railway’s advice, and what this tool covers

Railway advisesThis tool
Roll all environment variables, including API keys.Lists every variable, with its current value, in every workspace you can access. You rotate each one yourself.
Rotate database credentials (Regenerate on the database service).Does not change them. Marks them as database-credential, including pasted copies. See the checklist.
Roll any private registry credentials.Cannot. They are not variables. Do this by hand at Railway.
Review logs for unusual activity.Cannot. Do this by hand. The checklist lists every manual step with links to Railway’s posts.

Which workspaces it covers

  • All of them. The tool works through every workspace the signed-in administrator can access, and within each one every project, environment and service. You do not pick them one at a time.
  • You can leave workspaces out. Add their ids to skip_workspaces in the policy file. A skipped workspace is reported, so the audit is marked incomplete.
  • You sign in with the Railway CLI. The tool needs the Railway CLI and runs railway login, a browser sign-in as yourself. That one login reaches every workspace you can access. The tool never sees your token.
  • Nothing fails silently. A workspace where you lack permission is skipped and reported with the reason. A failure in one place never stops the rest.

Signing in and starting

  1. Sign in

    Press Sign in with Railway. The Railway CLI opens your browser. If you are already signed in, the status line says so. Railway invalidated all API tokens on 22 October 2026, so you will need to sign in again.

  2. Choose where to save

    The file goes in a new folder named run-YYYYMMDD-HHMMSS inside the folder you choose. The default is your Desktop. The folder is readable by you only.

  3. Audit

    Press Audit all my workspaces.

What it reads

  • Every variable. The variables of every service in every environment, and the shared variables of every environment.
  • Only reads. Nothing is written to Railway. Nothing is redeployed.
  • Values as stored. A reference such as ${Postgres.DATABASE_URL} appears as written, not as its resolved value. A variable that Railway hides from the API (a sealed variable) appears with an empty value.
  • Large accounts finish. The tool follows every page of results. Railway allows 1,000 requests an hour on Hobby and 10,000 on Pro, and tells the tool nothing more, so the tool counts its own requests and slows down if Railway says it is going too fast. You can cancel at any time.
  • A gap is never hidden. If a workspace, project or environment cannot be read, the rest still go on. Every gap is shown on the results screen, with the reason.

The results

The audit writes one file into a new run folder on your Desktop.

FileContentsHandle with care
audit.csvOne row for every variable: workspace, project, environment, service (or shared), variable, value, category and reason.Contains live secrets. Readable by you only (mode 0600). Keep it safe and delete it when you have finished.

The exact columns are in the man page railway-variable-auditor-csv(5). Open audit.csv in a spreadsheet. Values that contain commas, quotes or line breaks are quoted, so they come through intact.

The audit file holds every secret in one place

That is what makes it useful and what makes it dangerous. Store it on an encrypted disk, do not email it or put it in a shared folder, and delete it once you have rotated everything. The tool never prints a value to the terminal or to a log.

The category column is a hint

The tool sorts every variable into a group, to help you decide what to do first. It is only an opinion. Nothing is changed because of it, and when it is unsure it says so.

CategoryWhat it meansWhat you do
ini-configINI file content held in a variable. It often holds tokens for other systems such as Xero.Renew the tokens with each system.
database-roleThe password of an application role of a Postgres service, found through a connection URL on the private network.Change it in the database and in every variable that holds it.
database-credentialA credential for a Railway database such as PGPASSWORD or DATABASE_URL, a connection URL with a password in it, or a pasted copy of one.Use Regenerate on the database service. Replace pasted copies with references.
internal-hostnameNames another container on the private network, such as *.railway.internal.Nothing to rotate.
referenceThe whole value is one ${...} reference.Rotate the source variable.
unsharedUsed in one place only, or empty or unreadable (it may be sealed). Most likely an API key.Rotate it with its provider.
shared-configThe same value in more than one place, but it does not look like a secret, such as NODE_ENV.Nothing to rotate.
shared-manualA shared secret that looks like a key from another provider.Rotate it with its provider, then update every place that uses it.
sharedA shared secret with an internal secret name (SECRET, SALT, PEPPER, SESSION, COOKIE and similar), in a format that can be reproduced.Make one new value and set it everywhere it is used.

“Shared” means the same value anywhere in the audit: in two services, two projects or two workspaces. When you change a shared secret, change it everywhere at once, or the places will disagree.

Working through the file

  1. Check the gaps

    Read the results screen. Anything not read is not in audit.csv, and a secret shared with an unread place may look unshared.

  2. Sort by category and by value

    Sorting by the value column puts the places that share a secret next to each other.

  3. Rotate at the source

    Follow the checklist: databases first (Regenerate), then buckets, GitHub and registry credentials, then every third party key.

  4. Update Railway

    Set the new value in every variable that held the old one, then redeploy every service that uses it. Containers read variables only at startup.

  5. Run the audit again

    Compare the new file with the old one to find anything you missed. Then delete both files.

The command line

The same audit is available without a window, for scripts and for machines with no screen:

railway login
railway-variable-audit --out ~/railway-audit

It writes the same file, also to your Desktop unless you give --out, prints what it read and what it could not read, and never prints a value. The exit status is 0 when everything was read, 1 when something was skipped or failed, and 2 when it could not start. See the man page railway-variable-audit(1).

Next time

  • The policy file remembers your choices. policy.ini in your configuration folder holds the workspaces to skip, and extra names that mark a database credential or an internal secret. Both the window and the command line use it.
  • Every audit has its own folder, named by the date and time, so you can compare one with another.
  • Audit on a routine as well. A secret that was rotated last month is worth less to an attacker than one from last year.
The unshared keys and INI tokens may have been exposed too

The incident may have exposed every variable, not only the shared ones. This tool cannot rotate a key that belongs to another company. Go through audit.csv and rotate each one with its provider.
