Checklist: what to do by hand

The tool lists your variables. It cannot rotate them. Railway’s own posts give the steps, and this page points to them.

Where these steps come from

Everything on this page is Railway’s advice from its security disclosure and the recommendation posts that followed. This page summarises them. Follow Railway’s posts for the exact steps, because they may be updated.

Status

As of 22 October 2026, 06:29 UTC

On status.railway.com (incident QH8L8B3E), builds were available again for Pro and Enterprise workspaces, with other plans to follow. Railway also invalidated all API tokens at 04:17 UTC. Sign in again with railway login, and create new tokens for any scripts. Check the status page for the latest, because this changes.

A sensible order

  1. Database credentials

    Use Regenerate on each database service. Do not edit the password variable by hand and do not run ALTER USER. See Databases.

  2. Run the audit

    Use this tool to write audit.csv, the list of every variable in every workspace. Work through it row by row. Anything that could not be read is listed on the results screen. Deal with it first.

  3. Buckets, GitHub and registry credentials

    Railway already reset bucket credentials and invalidated GitHub tokens. Finish the steps below.

  4. Third party keys

    Rotate every key in audit.csv at its provider, and check usage.

  5. Set the new values and redeploy every consumer

    “Containers read variables only at startup”, so every service that uses a changed value must be redeployed. Then check the logs.

Databases

  • Other roles are yours to rotate. Application roles of a Postgres service (a role with its own password in a connection URL or a variable) are marked database-role in audit.csv. Change the password in the database, then in every variable that holds it, then redeploy. Rows marked database-credential are for the template’s own login and its pasted copies.
  • Regenerate the template’s own login, do not edit. On the database service, open the Database tab, Config, Connection, and click Regenerate next to the password. Railway changes the password inside the database and the variable together. The database restarts and drops every open session.
  • Replace pasted connection strings with references such as ${{ Postgres.DATABASE_URL }}. Services that reference the database variables pick up the change on their next deploy. Pasted copies do not. audit.csv marks pasted copies with the category database-credential.
  • Update outside consumers of the public connection URL by hand: local development, CI, reporting tools and scheduled jobs.
  • Railway’s posts: PostgreSQL MySQL Redis MongoDB.

Buckets

  • Railway invalidated and regenerated the access key and secret key of every bucket in every environment. The bucket name, address and objects are unchanged.
  • Redeploy every service that uses a bucket. Replace any pasted old key with a reference, then deploy. Update outside tools such as local development and CI.
  • Check each bucket for unexpected uploads or deletions. Buckets have no automatic backups.
  • Railway’s post: Redeploy buckets and reconnect GitHub.

GitHub and registry credentials

  • Reconnect GitHub. Railway invalidated the tokens it held for your GitHub connection. Reconnect your account, check the Railway GitHub App, and confirm each service’s repository and that autodeploy is on.
  • Registry credentials are not variables. Railway also removed GitHub tokens that were stored as registry credentials. Those tokens still work on GitHub until you revoke them. Revoke each one, create a new token with read:packages, and enter it in each service under Settings, Source, Registry Credentials. This tool cannot do this for you.
  • Check GitHub for unexpected access: Railway's post.

Third party keys

audit.csv marks the unshared variables, INI tokens and keys from other providers. They are most likely keys from other companies, and the tool cannot rotate them. For each one, rotate it at the provider, then check that provider for unexpected use. Railway has posts for these providers:

ProviderRailway’s post
AWSCheck for anomalous AWS access
Google CloudCheck for anomalous GCP access
StripeCheck for unexpected usage in Stripe
OpenAICheck for unexpected OpenAI usage
AnthropicCheck for unexpected Anthropic usage
GrokCheck for unexpected Grok usage
OpenRouterCheck for unexpected OpenRouter usage

Variables for tools that are not in this list, such as Xero, follow the same pattern: rotate the credential at the provider using the process that tool needs, then look for unusual activity.

Logs and audit logs

  • Review the logs of your services for unusual activity, as Railway advises.
  • Review the Railway audit log for variable reads, registry credential changes and deployments that your team or Railway Staff did not make. How long it is kept depends on your plan.
